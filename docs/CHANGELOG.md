## 2026-10-14 — Cloudinary-backed media storage (fixes production image uploads not persisting)

- Audited a 5-part pasted change request (changelog, Express body-size limits, Tailwind `content` array, static-asset path normalization, build verification). Two of the five parts didn't match this codebase: `express.json`'s body limit is irrelevant to multer's multipart handling (which already has its own 5MB limit, unchanged) — not touched. This project's Tailwind 4 setup is CSS-native (no `tailwind.config.ts`, no JS `content` array, and a full-repo scan found zero dynamically-interpolated Tailwind class strings) — the pasted "layout discrepancy" theory didn't apply; confirmed with the user that what they were actually seeing in production was the broken/missing images below, not a CSS purge bug — no Tailwind changes made.
- **Root cause (confirmed real)**: `backend/src/modules/catalog/mediaUpload.middleware.ts`/`mediaStorage.ts` wrote uploaded product/category/promotion images to local disk (`backend/uploads/`), served via `express.static` in `app.ts`. The backend runs on Render; local disk doesn't survive a redeploy/restart/multi-instance scaling, so every uploaded image eventually 404s in production — this is what the user was actually seeing.
- New `backend/src/integrations/media/` provider abstraction (mirrors the existing `integrations/email/` console/Brevo split): `CloudinaryMediaProvider` (required in production) and `LocalMediaProvider` (dev/test default, same disk behavior as before — chosen over "Cloudinary everywhere" so `npm test`/local dev need no external network dependency). Chosen via `getMediaProvider()`, gated by `env.media.provider`, forced to `cloudinary` in production the same way `MOCK` payments is forced out of production (`env.ts`'s `superRefine`).
- `mediaUpload.middleware.ts` switched from `multer.diskStorage` to `multer.memoryStorage()` — all MIME/size validation unchanged; the buffer now streams straight to the provider (Cloudinary's `upload_stream`, or the local provider's own disk write), never touching disk twice.
- `categories.controller.ts#uploadImage`, `promotions.controller.ts#uploadImage`, `variants.controller.ts#uploadMedia` now call the provider instead of building a local `/uploads/...` URL directly. `ProductMedia` gained a nullable `mediaPublicId` column (migration `add_product_media_public_id`) so `removeMedia` deletes the right asset from whichever provider created it — Category/Promotion image deletion was never wired to file cleanup before and still isn't (pre-existing gap, not a regression).
- New env vars `MEDIA_PROVIDER`/`CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` (`backend/.env.example`, `src/config/env.ts`), required in production via the same pattern as `DATABASE_URL`/`APP_URL`; the local provider is explicitly refused in production.
- `frontend/src/proxy.ts`: added `https://res.cloudinary.com` to the CSP's `img-src` — a gap found during implementation, not in the original request. Cloudinary serves images from its own CDN host, a different origin than the backend, which was the only host previously allowlisted; without this, every image would have been silently blocked by CSP once Cloudinary went live.
- **Known data cleanup needed**: existing DB rows with `imageUrl`/`url` pointing at `/uploads/...` paths from before this fix point at files that no longer exist — no automated migration is possible (the source files are gone); affected products/categories/promotions need their images re-uploaded manually once Cloudinary is live.
- Verification: backend `npm run build`/`lint` clean; `npm test` 697/701 passing (the 4 failures are the same pre-existing/unrelated ones already called out in the entry below — none touch media/catalog-upload code; the 13 media-upload tests, including a new `mediaPublicId` case, all pass). Frontend `npm run lint`/`npm run typecheck` clean (no frontend logic changed beyond the one-line CSP addition). Migration `add_product_media_public_id` applied to both the Neon dev database and the local test database (the latter needed an explicit `migrate deploy` with `DATABASE_URL` pointed at `DATABASE_URL_TEST`, since the CLI never reads that var automatically). **Requires a manual Render dashboard change** (outside this repo, not performed here): set `MEDIA_PROVIDER=cloudinary` + `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` in the backend's production environment, then redeploy.

## 2026-10-14 — Same-origin API proxy for the frontend/backend cross-site cookie gap

- Confirmed with user: the `/admin/dashboard` redirect loop persisted even after today's earlier `COOKIE_SAMESITE=none` fix (see entry below) — `SameSite=None` makes the cookie eligible to travel cross-site, but the browser and the server-rendered admin layout can still disagree about session state across different enforcement paths (third-party cookie blocking, browser privacy settings), since `frontend/src/lib/api.ts`'s client-side fetches hit the backend's absolute cross-origin URL (`https://vizaura-backend.onrender.com/api/v1`) rather than the frontend's own origin.
- Added a Next.js rewrite (`frontend/next.config.ts`) proxying `/api/v1/:path*` to the real backend origin, so browser-side requests become same-origin and cookies become first-party, independent of `SameSite`/third-party cookie policy. The rewrite's `source` deliberately mirrors the backend's own `/api/v1` prefix exactly — a user-proposed `/api/backend/*` prefix was rejected because the refresh-token cookie's `Path=/api/v1/auth` (`backend/src/security/cookies.ts`) is matched by the browser against the *requested* path, not the proxy destination; a mismatched prefix would have silently broken refresh-token delivery.
- `frontend/src/lib/api.ts`: `API_BASE_URL` is now environment-aware — client-side resolves `NEXT_PUBLIC_API_BASE_URL` (set to `/api/v1`, relative, in production, so requests go through the new rewrite); server-side (Server Components, via `auth-server.ts`/`server-fetch.ts`, which can't resolve a relative URL inside Node) always resolves an absolute backend URL via the new `API_BASE_URL_INTERNAL`, unaffected by the rewrite since those calls already forward the request's `Cookie` header manually.
- `frontend/src/proxy.ts`'s CSP builder (`apiOrigin()`) previously derived the backend's origin from `NEXT_PUBLIC_API_BASE_URL` for `img-src`/`connect-src` — product/category/promotion images are absolute URLs served directly from the backend (`backend/src/modules/catalog/mediaStorage.ts`), never proxied by the rewrite, so once `NEXT_PUBLIC_API_BASE_URL` became relative this would have silently dropped the backend host from the CSP allowlist and blocked all images. Fixed to resolve from the always-absolute `API_BASE_URL_INTERNAL` instead.
- New server-only env vars `BACKEND_ORIGIN` (`next.config.ts`) and `API_BASE_URL_INTERNAL` (`api.ts`/`proxy.ts`), documented in `frontend/.env.example`; local dev unchanged (`NEXT_PUBLIC_API_BASE_URL=http://localhost:4001/api/v1`, dev already works cross-port since `localhost` is same-site regardless of port). **Requires a manual Vercel dashboard change** (outside this repo): set `NEXT_PUBLIC_API_BASE_URL=/api/v1`, `BACKEND_ORIGIN`, and `API_BASE_URL_INTERNAL` in Production + Preview env vars.
- Backend untouched: CORS/`ALLOWED_ORIGINS`/`COOKIE_SAMESITE`/`cookies.ts` unchanged — Vercel's rewrite forwards the browser's real `Origin` header unmodified, so CSRF/CORS origin checks keep working exactly as before. Audited `frontend/src/lib/api/admin/{products,categories-mutations,promotions-mutations}.ts` (each duplicates the same `API_BASE_URL` fallback pattern for file-upload requests) — no code change needed there, since they already read `NEXT_PUBLIC_API_BASE_URL` first and will automatically pick up the relative path once it's set in Vercel.
- Verification: `frontend` `npm run typecheck` clean. `npm run lint` run. No browser tool available in this environment — the actual fix can only be meaningfully verified on a Vercel preview/production deploy (local dev doesn't exercise the rewrite); see `docs/CURRENT_TASK.md` for the manual verification checklist (login + no redirect loop, Network tab shows same-origin requests, Cookies tab shows first-party cookies with correct `Path`, images still load).

## 2026-10-14 — Cross-domain cookie fix + opt-in admin bootstrap startup hook

- Audited a 5-part pasted change request (auto-admin-bootstrap-on-boot, a single `res.cookie('token', ...)` cross-domain config, looser login/verification error handling, a frontend `localStorage`/`Authorization: Bearer` fallback, redirect-by-role). Found most of it already correctly implemented and the rest in direct conflict with this repo's non-negotiable auth rules: the frontend already has no `localStorage` usage anywhere, already sends `credentials: "include"` globally (`frontend/src/lib/api.ts`), and already redirects to `/admin/dashboard` vs `/account` based on permissions, not a role string (`LoginForm.tsx` + `lib/authorization.ts#hasAdminAccess`); login/register already distinguish unverified customers (allowed to sign in) from unverified staff (blocked, `403 AUTH_EMAIL_NOT_VERIFIED`). Adding `localStorage` or a `Bearer`-header fallback was rejected — it would violate "never localStorage" and weaken the cookie-only session model for no real benefit.
- The real gap, confirmed with the user: production deploys the frontend and backend on **unrelated registrable domains** (no shared parent domain), which `docs/AUTH_SECURITY.md` already flagged as unsupported. `backend/src/config/env.ts` previously *required* `COOKIE_DOMAIN` whenever `COOKIE_SAMESITE=none` — backwards for this topology, since a `Domain` attribute can only extend a cookie across subdomains of the *same* registrable domain, never bridge unrelated ones. Removed that requirement; `COOKIE_DOMAIN` now correctly stays unset (host-only cookies) for `SameSite=None` in this deployment shape. No change to `cookies.ts` (already never sets `Domain`) or `middleware/csrf.ts` (its Origin-header + custom-header checks are already independent of `SameSite`, so they remain the CSRF defense under `SameSite=None` — no double-submit-token mechanism added).
- New `backend/src/security/adminBootstrap.ts` extracts the super_admin-provisioning logic out of the existing manual-only `prisma/seed-admin.ts` so it can also run as an **opt-in, guarded startup hook** (`server.ts`, awaited before `app.listen`) — the user's hosting setup makes one-off ops commands impractical. Same guard rails as before: no-op unless `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` are both set (safe to leave wired into every boot), refuses production unless `SEED_ALLOW_ADMIN_BOOTSTRAP=true`, never creates a second `super_admin` (checked by role membership, not email), never overwrites an existing user's password. `BOOTSTRAP_ADMIN_*`/`SEED_ALLOW_ADMIN_BOOTSTRAP` moved into `env.ts`'s validated schema. `prisma/seed-admin.ts` is now a thin CLI wrapper around the shared function, kept for manual use; its result is now a status value so the CLI can still set a non-zero exit code on misconfiguration, matching its prior behavior.
- Updated `docs/AUTH_SECURITY.md` (Cookies, CSRF, new "Super_admin Bootstrap" section) and `backend/.env.example` to describe both deployment topologies and the startup hook.
- Verification: `backend` `npm run build`/`npm run lint` clean; `tests/integration/seed-guard.test.ts` (2/2) and `tests/integration/auth/*` (56/56) passing; full backend suite re-run, only 4 pre-existing/unrelated failures (`catalog.products.test.ts`, `customers.test.ts`, `catalog.categories.admin.test.ts`, `requireCaptcha.test.ts` — none touch auth/cookies/env), consistent with the pre-existing flakiness already noted in the 2026-10-08 entry. `frontend` `npm run build` clean (no frontend files changed).
